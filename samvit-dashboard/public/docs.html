DQS for Samvit

DQS checks the screening records Samvit's workers send and reports how far the data can be relied on. Where it cannot be, DQS names the worker, the field and the rule responsible.

This page has four parts. The API section describes how records are sent. Record rules are checked on each record as it arrives, and their results come back in the API response. Dataset rules look at many records together, such as a worker's week. Architecture shows how the parts of DQS fit together.

API

Sending records

Each Avni form is sent to DQS as one record, in one request, when it is completed. DQS checks the record against Samvit's record rules straight away and returns every rule's result in the response. It also stores the record and its results for reporting.

Addresses

There is one address for each of the 5 record types. Each takes a POST request with a JSON body.

AddressRecord type
/v1/samvit/records/registrationPerson registration
/v1/samvit/records/cbacCBAC form
/v1/samvit/records/oral_screeningOral screening
/v1/samvit/records/clinician_reviewClinician review of an oral screening
/v1/samvit/records/oral_imageOne photograph from an oral screening

The running service also describes these addresses at /docs and /openapi.json.

Authentication

The service has no login or API key of its own. Whoever runs it controls who can reach it, for example through a gateway or a private network.

Request body

The body is a flat JSON object: one key per field, with no wrapper around it. The fields for each record type are listed below.

  • Dates are written 2026-09-22. Dates with times are written 2026-09-22T10:40:00+05:30. A time sent without the +05:30 part is read as UTC.
  • true or false fields take JSON true and false, or the text "true" and "false". 1 and 0 are not accepted.
  • Numbers may be sent as JSON numbers or as text such as "52".
  • A field with no value can be left out or sent as null.
  • A field marked Worked out by DQS does not need to be sent. A value sent for it is replaced.
  • A field marked Filled in by DQS does not need to be sent either. DQS fills it in when it is left out; a value that is sent is kept.
  • A missing Required field does not stop the record being checked. The response carries a warning naming it. A record without record_id or beneficiary_id is refused.
  • A field not listed for the record type is stored with the record and ignored by the rules. The response carries a warning naming it.
  • Sending a record again with the same record_id replaces the stored copy and checks it again.

Personal data

Personal data is handled before anything is stored or checked. The Stored as column in the field tables gives the handling for each field.

  • A person's name and phone number are replaced by a code. The same value always gives the same code, so records for one person can still be matched. The code cannot be turned back into the name or number without a secret key, which is held by whoever runs the service. A name also gets a second code for how it sounds, so that two spellings of one name can be matched.
  • An Aadhaar, UID or Voter ID number, the full address and the clinician's notes are removed. Only the fact that a value was sent is kept.
  • The Avni beneficiary ID is kept as sent, so that any record can be traced back to Avni.

Response fields

evaluation.rulepack_id
The version of Samvit's rules the record was checked under. Stored with the result, so an old result can be explained after the rules change.
evaluation.record_id
The record_id sent.
evaluation.violations
Problems with the fields themselves: a value that cannot be read, a required field that is missing, a field that is not listed. Each has a code, a level and a message. A level of error means the record could not be read and was not checked. A level of warning means it was checked anyway.
evaluation.outcomes
One entry per rule: the rule's ID and version, its outcome, and for a failure the evidence, which holds the supervisor message and the values the rule was decided on. blocked_on names the facts about the person that were missing when the outcome is indeterminate.
evaluation.profile_updates
Facts this record adds to what DQS knows about the person, such as age, with the date they hold from. Later records for the same person are checked against them.
evaluation.scored
false when the record could not be read.
summary
How many rules gave each outcome: overall, by area (by_feeds) and by kind of rule (by_dimension). In by_feeds, provenance is genuineness evidence of a real visit and suspicion is genuineness signs of invented data. See Record rules.

Outcomes

OutcomeMeaning
passThe record meets the rule.
failThe record does not meet the rule. The evidence says why.
not_applicableThe rule does not cover this record, such as a referral-reason rule on a record with no referral.
indeterminateThe rule needs a fact about the person that DQS does not have yet, such as their registration date or sex.
not_evaluatedA dataset rule. It is worked out later over many records. See Dataset rules.
errorThe rule could not be worked out on this record. evidence.error says why.

Record rules

Rules checked on each record

These 38 rules are checked on each record as it arrives. Their results come back in the API response. Each rule belongs to one of three areas.

Sufficiency

Whether enough was recorded to judge the record: questions answered, photographs taken, reasons given.

Genuineness

Whether the record comes from a real visit. It has two parts that are always reported separately. Evidence of a real visit, such as a location inside the village. Signs of invented data, such as a form finished before the visit.

Missing evidence, as in an area with poor phone signal, does not count as a sign of invented data.

Quality

Whether the recorded values are in range, add up, and agree with each other.

A supervisor message is what a supervisor reads when the rule fails. Words in square brackets are filled in from the record.

Dataset rules

Rules over many records

These 8 rules look for patterns that only show across many records: a worker's week, several weeks, or all the workers in the district. One record cannot pass or fail them, so each appears in the API response with the outcome not_evaluated. Their results appear in the reports and on the dashboard, for each worker and each week.

Most of them look for signs of invented data, such as forms entered faster than screenings can be done or answer sets that repeat. Three measure how often the worker, the AI and the clinician agree about the oral photographs. Those three do not pass or fail.

API

Receives each record, codes or removes personal data, checks the record against the record rules, stores the record and its results, and returns the results. It checks against the version of Samvit's rules that was most recently published when it started.

DQS database

Holds Samvit's configuration: the record types and their fields, which rules apply and their settings, the village boundaries, and every published version of the rules. It also holds every record as stored, after personal data is handled, and each record's rule results, marked with the version of the rules that produced them.

Extract process

Runs on a schedule. It copies new and changed records and results into the reporting database and links each record to its worker, village and taluk as they were on the visit date. It works out the dataset rules and adds the results up for each worker and each taluk, week by week.

Reporting database

A separate database, so that reports do not slow the API down. It holds the copied records and results, the lists of workers, villages and devices, and the weekly results and scores.

Dashboard

A web page that shows each worker's and each taluk's scores by week, and the rules behind them. It reads a file written from the reporting database by dqs dashboard export, so it shows the scores as of the last export.

Scores

A single record has no score. Results are added up for each worker for each week, Monday to Sunday by visit date, and for each taluk for each week. Each gets a score for sufficiency, for the two parts of genuineness, and for quality, and an overall trust figure. The three areas are always shown next to the trust figure.

A worker is compared with the other workers in the same district. A week with fewer than 20 records is marked as not having enough data, and is not scored. One rule that fails often pulls its area's score down sharply, and passing rules do not hide it. The trust figure starts from quality and is lowered by signs of invented data and by low sufficiency. Weak evidence of a real visit does not lower it. It makes the trust figure less certain. Every score names the version of the rules it was worked out under.

Changing a rule

Rules, settings and fields are configuration. A change to them needs no change to the program.

  1. Edit Samvit's configuration file, tenants/samvit/samvit.yaml: change a setting, add or remove a rule, or add a field.
  2. Load it into the DQS database: dqs config import tenants/samvit/samvit.yaml.
  3. Publish: dqs publish --tenant samvit. This checks the configuration and creates a new numbered version of Samvit's rules. The API uses it from its next restart.
  4. Re-check the stored records under the new version: dqs rescore --tenant samvit --all.
  5. Run the extract so the reports show the new results and the scores are worked out again: dqs etl run --tenant samvit --all.
  6. Write the scores for the dashboard: dqs dashboard export --tenant samvit --out dashboard.json, into the folder the dashboard page is served from.
